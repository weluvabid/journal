## Short answer

Hydration attaches client-side behavior to server-rendered markup and reconciles it with the framework’s expected tree. Islands architectures hydrate only selected interactive regions, leaving static content as HTML.

## Reason from first principles

Hydration requires server and client output to agree. Nondeterministic dates, random IDs, browser-only state, or locale differences can create mismatches. Islands reduce shipped JavaScript but introduce boundaries for shared state and interaction.

## A concrete example

```astro
<StaticArticle />
<SearchPanel client:idle />
```

## Boundary cases to reason through

Hydration mismatches are frequently caused by values that differ between server and browser: random numbers, current time, locale formatting, viewport reads, and browser storage. Keep browser-only reads behind client lifecycle boundaries. Islands also need explicit data boundaries; two independently hydrated components do not automatically share one in-memory state store.

## Common misconception

SSR does not mean zero JavaScript, and hydration is not the same as rendering HTML.

## Why this matters in production

Choose hydration strategies per interaction urgency. Measure transferred JavaScript, hydration cost, and time to usable controls.
