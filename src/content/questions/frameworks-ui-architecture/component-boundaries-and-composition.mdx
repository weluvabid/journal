## Short answer

A useful component boundary groups behavior and presentation that change together while exposing a small, meaningful contract. Composition is often more flexible than a large component with many boolean modes.

## Reason from first principles

A component is not automatically reusable because it appears twice. Premature abstraction can couple unrelated screens; duplicated markup may be cheaper until the shared behavior stabilizes. Prefer slots/children and data-driven primitives over dozens of flags.

## A concrete example

```svelte
<Card>
  <CardHeader>Account</CardHeader>
  <CardBody><AccountSummary /></CardBody>
</Card>
```

## Boundary cases to reason through

A good public component API exposes stable user intent, not every implementation detail. Avoid booleans whose combinations create ambiguous states; prefer named variants or composed subcomponents. Before extracting a shared component, identify the behavior that is genuinely shared and the parts that should remain customizable by the consuming feature.

## Common misconception

“One component per file” and “DRY at all costs” are not architecture principles.

## Why this matters in production

Good boundaries make testing, accessibility, ownership, and independent iteration easier.
