## Short answer

A controlled component receives its value and emits change intent; its parent is the source of truth. An uncontrolled component owns its current state and may expose an initial value or imperative handle.

## Reason from first principles

Controlled APIs make state coordination and validation explicit but add wiring. Uncontrolled APIs reduce parent involvement and can improve integration with native forms. Mixing both without a clear precedence rule creates hard-to-debug state divergence.

## A concrete example

```svelte
<!-- Conceptual contract: value is supplied; change is reported upward. -->
<CustomInput value={name} onChange={setName} />
```

## Boundary cases to reason through

Controlled text inputs must preserve the exact value the browser reports during composition; rewriting it on every keystroke can break IME input. An uncontrolled field’s `defaultValue` is an initial value, not a live synchronization channel. Define reset behavior explicitly, especially when a form is reused for a different record.

## Common misconception

Controlled does not mean “the parent must rerender on every keystroke” in every architecture, and uncontrolled does not mean untestable.

## Why this matters in production

Document ownership, default-value behavior, reset semantics, and whether external changes are reflected after mount.
