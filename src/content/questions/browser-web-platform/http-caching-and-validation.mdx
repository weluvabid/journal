## Short answer

A fresh cached response can be reused without contacting the origin. A stale response may be revalidated with validators such as ETag or Last-Modified; the server can respond `304 Not Modified`. Cache directives control reuse and storage.

## Reason from first principles

`Cache-Control: max-age` defines freshness lifetime; `no-cache` permits storage but requires validation before reuse; `no-store` prohibits storage. `private` and `public` matter for shared caches. Query-string versioning is useful for immutable assets but not a substitute for correct policy.

## A concrete example

```http
Cache-Control: public, max-age=31536000, immutable
```

Use this for content-hashed static assets, not mutable HTML.

## Boundary cases to reason through

A `304` response has no replacement representation body; the browser reuses the stored representation after validation. Be careful with personalized responses: a shared cache must not reuse one user’s response for another. Content-hashed assets can be immutable for a long time, while HTML generally needs a short freshness lifetime or revalidation so deployments do not strand users on deleted chunks.

## Common misconception

`no-cache` does not mean “do not cache.”

## Why this matters in production

A good policy separates immutable fingerprinted assets from HTML and user-specific responses. Incorrect shared caching can leak personalized content.
