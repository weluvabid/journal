## Short answer

Create an AbortController per logical operation and pass its signal to APIs that support cancellation. Abort when the result is no longer needed, such as on navigation, component teardown, or a newer search query.

## Reason from first principles

Cancellation is cooperative. An abort signal does not undo server-side work already performed and does not automatically cancel APIs that ignore the signal. Handle `AbortError` as an expected outcome while allowing unrelated errors to propagate.

## A concrete example

```js
const controller = new AbortController();
const response = await fetch(url, { signal: controller.signal });
// Later, when obsolete:
controller.abort();
```

## Boundary cases to reason through

A signal is one-shot: after aborting a controller, create a new controller for the next independent operation. Use `AbortSignal.timeout()` or combine signals where supported, with a fallback if the target browser matrix requires it. For latest-request-wins UI, cancellation saves work, but a request sequence/token check is still a useful correctness guard.

## Common misconception

Aborting a fetch is not a transaction rollback and does not guarantee the server did not process the request.

## Why this matters in production

Use request identity or sequence numbers to prevent stale responses from overwriting newer UI state. Pair cancellation with idempotency for mutations.
