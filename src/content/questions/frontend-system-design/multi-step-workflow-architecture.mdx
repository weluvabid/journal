## Short answer

Represent the workflow as explicit steps and transitions, persist only what is safe and necessary, and let the server remain authoritative for committed business operations. Each transition needs validation and a recovery path.

## Reason from first principles

A browser flow is not a distributed transaction. Payment authorization, inventory reservation, and account creation may succeed independently. Use server-side workflow orchestration, idempotency keys, and compensating actions for cross-service failures.

## A concrete example

```ts
type Checkout =
  | { step: 'cart' }
  | { step: 'address'; cartId: string }
  | { step: 'payment'; orderDraftId: string }
  | { step: 'complete'; orderId: string };
```

## Boundary cases to reason through

Persist durable server-side workflow identifiers, not just a client-side step number. A browser refresh should reconstruct the current authoritative state from the server. If payment succeeds but the response is lost, the client needs a way to query the operation by idempotency key or order ID rather than blindly submitting payment again.

## Common misconception

Persisting a client-side step does not prove the server completed that step.

## Why this matters in production

Plan refresh/re-entry, duplicate submissions, expired sessions, back navigation, payment retries, and partial failures.
