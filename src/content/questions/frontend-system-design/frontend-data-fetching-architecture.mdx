## Short answer

Treat server state as a cache of remote authority, not as ordinary local UI state. Centralize request identity, caching, deduplication, invalidation, cancellation, and mutation reconciliation in a mature data-fetching library.

## Reason from first principles

A cache key must include every input that changes the response, including tenant/user scope where relevant. Invalidation should be precise enough to avoid stale reads but broad enough to preserve correctness. Avoid writing a custom query cache unless the product has a compelling reason.

## A concrete example

```ts
const queryKey = ['projects', { organizationId, status, page }];
```

## Boundary cases to reason through

Cache keys must include all variables that affect the server response and must be scoped to the active identity or tenant. On logout or account switch, remove or isolate private cached data. Decide whether mutations update a cache entry, invalidate related queries, or require a full refetch; these are consistency decisions, not merely library configuration.

## Common misconception

A successful HTTP response does not mean every component should independently own a copy forever.

## Why this matters in production

Define stale-time and retry policy, auth transitions, optimistic update behavior, and cache isolation between identities.
