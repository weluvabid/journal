## Short answer

A design system is a product with versioned foundations, components, accessibility contracts, documentation, and contribution governance. Separate semantic tokens from component implementation so themes can evolve coherently.

## Reason from first principles

A component library without adoption guidance and migration policy is not a complete design system. Avoid exposing every internal styling detail as public API. Define supported variants, deprecation windows, visual regression coverage, and ownership.

## A concrete example

```css
:root {
  --surface: var(--color-neutral-0);
  --text-primary: var(--color-neutral-950);
}
[data-theme='dark'] {
  --surface: var(--color-neutral-950);
  --text-primary: var(--color-neutral-50);
}
```

## Boundary cases to reason through

Governance matters as much as code: define who approves tokens, how deprecations work, how consumers learn about breaking changes, and what accessibility guarantees are part of the contract. Avoid exposing private implementation props that prevent future refactors. Adoption should be measured through real product usage, not the number of published components.

## Common misconception

More variants and props do not necessarily make a component more flexible.

## Why this matters in production

Version tokens and components together where possible. Treat accessibility and theming as contract tests, not optional polish.

## Interviewer follow-ups

- How do you handle breaking changes?
- How do you prevent design-token drift across apps?
