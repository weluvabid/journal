## Short answer

Virtualization renders only the visible window plus overscan. It is valuable when DOM size and rendering work become a measured bottleneck; it is unnecessary overhead for modest lists.

## Reason from first principles

A robust virtualizer must preserve stable item identity, calculate offsets, handle resize and dynamic heights, maintain keyboard navigation, and avoid scroll jumps. Overscan trades memory/work for smoother scrolling.

## A concrete example

```ts
const start = Math.max(0, firstVisible - overscan);
const end = Math.min(items.length, lastVisible + overscan);
const visible = items.slice(start, end);
```

## Boundary cases to reason through

Variable-height rows require measurement and offset correction; assuming a constant row height creates scroll drift. Preserve a stable key for each item so recycled DOM nodes do not retain the wrong focus or state. A virtualized list also needs a meaningful accessibility model and predictable keyboard navigation; rendering fewer nodes is not worth making the data inaccessible.

## Common misconception

Virtualization does not make data fetching, filtering, or sorting free.

## Why this matters in production

Prefer pagination or server-side filtering when users do not need a continuous huge list. Test screen readers and focus retention.
