## Short answer

Apply a reversible local change, send the mutation, then reconcile with the authoritative response. On failure, restore or invalidate the affected state. Serialize or version overlapping mutations when order matters.

## Reason from first principles

A naive rollback can overwrite a newer successful change. Capture a mutation ID or prior version, and only roll back if the optimistic version is still current. Idempotency keys help the server deduplicate retried mutations.

## A concrete example

```ts
const mutationId = crypto.randomUUID();
applyOptimistic(change, mutationId);
try {
  reconcile(await save(change), mutationId);
} catch (error) {
  rollbackIfCurrent(mutationId);
  throw error;
}
```

## Boundary cases to reason through

Suppose mutation A and mutation B both update the same record. If A fails after B succeeds, blindly restoring A’s old snapshot erases B. Associate optimistic writes with mutation/version identity and only roll back the state still owned by that mutation. Reconcile from authoritative server data after success, especially when the server normalizes values.

## Common misconception

“Undo the previous value on error” is unsafe when concurrent updates are possible.

## Why this matters in production

Define conflict behavior, retry semantics, offline behavior, and user-visible pending/error states before shipping optimistic interactions.
