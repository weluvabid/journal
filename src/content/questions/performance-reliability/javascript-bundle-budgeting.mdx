## Short answer

Measure route-level JavaScript, identify high-cost dependencies and execution paths, then defer code that is not needed for the initial experience. Code splitting helps only when the deferred code is not immediately fetched and executed anyway.

## Reason from first principles

Dynamic imports create chunk boundaries, but too many tiny chunks can increase request and coordination overhead. Tree shaking requires static analyzability and correct side-effect metadata. Reduce unnecessary client hydration as well as bundle bytes.

## A concrete example

```js
const Editor = lazy(() => import('./Editor.js'));
```

## Boundary cases to reason through

Splitting code can improve the initial route while making a later interaction slower if its chunk is fetched only after the user clicks. Preload only when the probability and urgency justify it. Inspect duplicate versions of dependencies and expensive initialization, not just compressed byte size; parse and execution cost can dominate on slower CPUs.

## Common misconception

A smaller compressed bundle can still be expensive to parse and execute, and a large split bundle may still be downloaded eagerly.

## Why this matters in production

Track initial and interaction-triggered JS separately. Test on constrained CPUs and realistic network profiles.
