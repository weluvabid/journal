## Short answer

The main thread must process input, script, style, layout, and paint. Long uninterrupted tasks delay all of them. Chunk work and yield between chunks, or move isolated CPU work to a Web Worker.

## Reason from first principles

`setTimeout` yields but adds task scheduling delay. `scheduler.yield()` can provide a more direct cooperative yield where supported; feature-detect it and retain a fallback. Workers avoid DOM access and require message/data-transfer design.

## A concrete example

```js
for (const chunk of chunks) {
  process(chunk);
  await new Promise((resolve) => setTimeout(resolve, 0));
}
```

## Boundary cases to reason through

A worker cannot access the DOM, so it is best for pure computation or APIs designed for worker contexts. Large structured-clone messages can erase the benefit; transferable ArrayBuffers avoid copying ownership-heavy binary data. Chunking on the main thread remains useful for smaller jobs when moving the work would add more coordination than value.

## Common misconception

Moving work to a worker does not make serialization, copying, or coordination free.

## Why this matters in production

Choose chunk sizes from responsiveness goals, use transferable buffers for large binary payloads, and handle worker errors/termination.
