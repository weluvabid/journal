## Short answer

Use `await` for dependent steps, `Promise.all` for independent work that must all succeed, and `Promise.allSettled` when each outcome must be inspected. Bound concurrency when fan-out can overwhelm a dependency.

## Reason from first principles

`Promise.all` rejects as soon as one input rejects, but it does not cancel the other operations. A rejected aggregate is not rollback. If cancellation matters, propagate an `AbortSignal` to operations that support it.

## A concrete example

```js
const [profile, settings] = await Promise.all([
  fetchProfile(userId, { signal }),
  fetchSettings(userId, { signal }),
]);
```

## Boundary cases to reason through

If one branch fails, decide whether sibling work should continue, be aborted, or produce partial output. `Promise.allSettled` is appropriate when every outcome matters; a concurrency limiter is appropriate when the input collection is large. Preserve the original error as a cause when adding domain context, and do not turn cancellation into a user-visible failure.

## Common misconception

`Promise.all` does not make work transactional or automatically stop sibling requests.

## Why this matters in production

Unbounded `Promise.all(items.map(...))` can exhaust sockets, rate limits, memory, or downstream capacity. Use a concurrency limiter for large collections.
