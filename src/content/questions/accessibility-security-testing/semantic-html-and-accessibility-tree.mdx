## Short answer

Semantic elements communicate role, name, state, and relationships to browsers and assistive technologies while providing built-in interaction behavior. They also improve keyboard support, maintainability, and machine interpretation.

## Reason from first principles

A `<button>` has activation and focus behavior; a clickable `<div>` does not. Landmark elements help navigation. Accessible names come from labels and content relationships, not from visual appearance alone.

## A concrete example

```html
<main>
  <h1>Account settings</h1>
  <button type="button">Save changes</button>
</main>
```

## Boundary cases to reason through

A label contributes to a control’s accessible name, while `aria-describedby` supplies supporting description. Native buttons, links, inputs, and headings expose behavior and relationships that custom elements must otherwise recreate. Inspect the accessibility tree and use a screen reader for important flows; automated checks cannot fully judge whether names and announcements make sense.

## Common misconception

ARIA should not be used to recreate native semantics that already exist.

## Why this matters in production

Start with semantic HTML, test keyboard-only use, inspect the accessibility tree, and add ARIA only to fill a genuine semantic gap.
