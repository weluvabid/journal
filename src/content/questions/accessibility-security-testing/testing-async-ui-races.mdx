## Short answer

Use deferred promises or controllable network handlers to force the ordering under test. Assert that stale results cannot overwrite newer state and that cancellation/error states are handled correctly.

## Reason from first principles

A sleep-based test assumes scheduler timing and is inherently fragile. Use fake timers only for timer behavior; use explicit promise resolution to test concurrency ordering.

## A concrete example

```ts
const first = deferred<Result>();
const second = deferred<Result>();
startSearch('a', first.promise);
startSearch('ab', second.promise);
second.resolve(resultFor('ab'));
first.resolve(resultFor('a'));
expect(screen.getByText('ab results')).toBeVisible();
```

## Boundary cases to reason through

Use deferred promises or a network mock to resolve requests in deliberately reversed order. Assert both the visible result and the absence of stale side effects. Also test unmount during an in-flight request, abort rejection, duplicate submit, and retry. Avoid sleeps: tests should control the event ordering they need to prove.

## Common misconception

Testing only the final happy path does not expose response reordering bugs.

## Why this matters in production

Test cancellation, unmount during work, duplicate submit, timeout, retry, and error propagation. Unknown execution paths should fail loudly rather than disappear into logs.
