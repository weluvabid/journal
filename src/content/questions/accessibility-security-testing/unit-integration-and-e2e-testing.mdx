## Short answer

Unit tests verify isolated logic; integration tests verify collaborating modules and boundaries; end-to-end tests verify critical user journeys through the running application. The strongest suite uses many fast focused tests and a smaller set of high-value browser journeys.

## Reason from first principles

Mocking every dependency can make tests validate the mock rather than the system. E2E tests are slower and more failure-prone, so keep them focused on externally observable contracts. Test accessibility and error states, not only happy paths.

## A concrete example

```ts
expect(rankSearchResults(index, 'event loop')[0]?.id).toBe('event-loop-tasks-and-microtasks');
```

## Boundary cases to reason through

Test behavior at the narrowest boundary that still proves the contract. Keep pure transformations in unit tests, verify actual component and browser API integration in integration tests, and reserve end-to-end tests for a small number of critical user journeys. Avoid mocking the module under test or replacing every collaborator with a mock that simply repeats the expected result.

## Common misconception

A high coverage percentage does not prove meaningful behavior is tested.

## Why this matters in production

Test boundary conditions, retries, invalid states, keyboard flows, and regression-prone integrations. Make tests deterministic and diagnostic.
