## Short answer

Browsers automatically attach matching cookies to requests, which creates CSRF risk for state-changing endpoints. Use appropriate SameSite settings plus server-side CSRF defenses such as tokens and Origin/Referer validation according to the threat model.

## Reason from first principles

SameSite=Lax reduces many cross-site cookie sends but does not eliminate every CSRF scenario. GET should not perform state changes. CORS is not a general CSRF defense because the request may still be sent.

## A concrete example

```http
Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax; Path=/
```

## Boundary cases to reason through

CSRF depends on ambient credentials being attached to a request the attacker can cause. SameSite reduces cross-site cookie sending but must be evaluated against redirects, embedded flows, and browser behavior. Validate Origin or Referer where appropriate and use anti-CSRF tokens for sensitive state changes. Never make a GET endpoint mutate state.

## Common misconception

CORS and CSRF solve different problems.

## Why this matters in production

Protect sensitive mutations, validate content types/origins, rotate sessions, and avoid state-changing links. Consider embedded/third-party contexts when choosing SameSite.
