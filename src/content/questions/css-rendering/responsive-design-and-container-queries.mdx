## Short answer

Prefer layouts that adapt intrinsically, then add breakpoints when the composition genuinely changes. Container queries let a component respond to the space it receives rather than the viewport alone.

## Reason from first principles

A viewport breakpoint answers “how wide is the screen?” A container query answers “how much space does this component have?” Fluid functions such as `clamp()` interpolate within bounds.

## A concrete example

```css
.card-grid {
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr));
}
.card-title {
  font-size: clamp(1.1rem, 2vw, 1.6rem);
}
```

## Boundary cases to reason through

A component can be narrow inside a wide viewport—for example, in a sidebar or split pane—so viewport-only media queries cannot describe its available space. Container queries solve that local constraint. Still test at 200% zoom and with text enlargement: a layout that only works at common device widths is not truly responsive.

## Common misconception

Responsive design is not a set of device-specific widths.

## Why this matters in production

Test content extremes, localization, browser zoom, and nested layouts. Container queries are especially useful for reusable cards and embedded panels.
