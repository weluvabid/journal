An unbounded queue is how you pretend the consumer is keeping up. The difference sits in memory until latency is embarrassing or the process falls over. Backpressure is admitting the rates don't match, and choosing what a person sees when they don't. Wait, retry, get rejected, or watch the job sit.

On the Shopify path the stages are ordinary and still easy to lie about. HTTP handler, publish, queue, worker, database, object storage. They do not share a speed. A worker can pull faster than the database commits. A report can be produced faster than storage will take the object. More concurrency helps until the downstream thing saturates. After that it's extra retries fighting over the same limit.

So the limits have to be actual numbers. In-flight cap, bounded buffers, timeouts, payload size, and a policy for a message that cannot be processed. A cap with no policy is just a crash on a different line.

The Shopify-facing Cloud Run service is not the Pub/Sub worker, and neither of those is a one-shot migration or maintenance job. Request lifetime and a process that sits on a subscription are different runtimes. Pull concurrency belongs on the worker. If the service starts consuming "just for this one path," there are two worker pools and only one of them is obvious.

I want one worker instance before any autoscaler. Throughput, backlog growth, processing time, what the database does under that. Scale from measured backlog and what one instance can finish, not from the fact that the slider goes higher.

Retries are how a small outage gets bigger. Retrying everything immediately is a self-DDoS. Backoff with jitter. A dead-letter path so a poison message doesn't sit at the head forever.

At-least-once means the same logical operation runs more than once. That's the contract, not an edge case. Handlers need a stable operation id, a uniqueness constraint, or a transition that's a no-op the second time. Ack before the write is durable and you drop work. Ack after the write, with no idempotency, and a lost ack applies it twice.

Cancel work whose caller is gone, when stopping is actually safe. On shutdown: stop pulling, finish or release what's in flight inside the termination budget, don't ack what you didn't finish. The gauges I care about are dull. Depth, age of the oldest message, processing time, retry count, in-flight, downstream errors. If oldest-age climbs, the queue is not "buffering."

What overload means depends on the promise. Some requests should fail fast. Some can wait inside a bounded window. Low-priority work can be dropped. Fulfillment work shouldn't vanish. Accept it durably or fail it where someone can see. The policy has to be the one already tested with the producer faster than the consumer, for longer than a demo.

```text
Publish: 120 jobs/s
Commit:   80 jobs/s
Growth:   40 jobs/s
10 min:   24,000 queued jobs
```

Illustrative rates, not FulfillmentGuard measurements. If the consumer stays 40 jobs/s behind, the queue is accumulating work, not absorbing a brief burst.
