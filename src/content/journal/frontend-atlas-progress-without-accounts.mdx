An account is a second product: registration, sessions, password recovery, email, deletion, persistence and support. Sometimes that infrastructure is justified, but I didn't feel that remembering which questions were completed was a good enough reason. Frontend Atlas is a reference guide, not a multiplayer application. I wanted the reading experience to earn that complexity first.

Frontend Atlas needs to remember which questions have been completed and where the reader stopped. Progress is stored in the browser. It won't move between devices automatically, but it can be transferred explicitly using a QR code.

Progress is a small, versioned store keyed by an immutable question id. The title can change or the article can move; the ID stays the same. Data is validated when it is read. If nothing is stored or the data is invalid, the guide shows no saved progress. Clearing site data or changing browsers will lose the local copy unless it has been exported.

Progress can be exported as a QR code. The manifest is an ordered, append-only list of question IDs. That way, an older export still refers to the same questions even after new ones have been added. Version 1 starts with `FATL1:`. Each question uses two bits. The manifest supports up to 150 questions, so the status bitset uses at most `ceil(150 × 2 / 8) = 38` bytes. Reading positions are stored separately using fixed-width entries. The payload also contains the manifest fingerprint and a checksum. Anyone with access to the QR code can inspect its progress data.

| State       | Encoded value | Meaning                 |
| ----------- | ------------- | ----------------------- |
| Not started | `00`          | No progress recorded.   |
| In progress | `01`          | Started, not completed. |
| Completed   | `10`          | Marked finished.        |

Merge takes the completed questions from both snapshots. If both snapshots have a reading position, the higher one is kept. Replace uses the imported snapshot as-is. Before applying any changes, the import checks the format version, manifest fingerprint, indexes and bounds. If the QR image is corrupt, it is rejected before the stored progress is changed.

Progress has to be transferred manually. After importing it, the two browsers can be changed independently until the progress is exported and imported again. Both devices need to be available for the transfer. Automatic sync, shared workspaces and recovery after a wiped device would need a server. I haven't built that for this reference guide.

The wire format and its tests are in the repo. Progress stays in the current browser and can be exported or imported as a QR code.

```text
Question state: 00 not started · 01 in progress · 10 completed
150 questions × 2 bits = 300 bits = 38 bytes (rounded up)
```

## Where it could go Next

I would also like to include a few small features. One of these would be the ability to favourite articles in the journal. As there is a maximum of 150 articles, this would take up very little space. If each article had a bit to represent if it was a favourite, this would only take up a total of 19 bytes of data. This means that it can be easily included in the QR export, as well as not increasing the QR code much. Users can favourite articles, easily find them and delete them when they have finished.
