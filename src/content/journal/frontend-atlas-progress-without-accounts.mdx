An account is a second product: registration, sessions, password resets, email, deletion, retention and support. Sometimes that infrastructure is justified. Remembering which questions I finished was not enough of a reason to build it. Frontend Atlas is a handbook, not a multiplayer app. I wanted the reading experience to earn that complexity first.

Frontend Atlas has to remember which questions you finished and where you stopped reading. Progress stays in the browser. Moving it to another device is a separate problem, handled by an explicit QR transfer rather than a login.

Progress is a small, versioned record in the browser, keyed by an immutable question id. The id does not change when the title changes or the article moves. Stored data is validated on read. Missing or malformed storage is shown as unsaved progress instead of a misleading `0% complete`. Clearing site data or switching browsers loses the local copy unless it was exported.

Export turns the progress record into a QR image. Its manifest is an ordered, append-only list of question IDs, so an old export keeps referring to the same questions after new ones are added. Version 1 starts with `FATL1:` and stores two bits per question. The manifest allows up to 150 questions, so the status bitset uses `ceil(150 × 2 / 8) = 38` bytes at the maximum, before the envelope and reading-position records. Reading positions use fixed-width entries alongside the bitset. The payload carries the manifest fingerprint and a checksum. Anyone with the QR image can inspect its progress data.

| State | Encoded value | Meaning |
| --- | --- | --- |
| Not started | `00` | No progress recorded. |
| In progress | `01` | Started, not completed. |
| Completed | `10` | Marked finished. |

Merge keeps completions from either snapshot and takes the higher reading position when both contain one. Replace uses the imported snapshot. Before local progress changes, import checks the format version, manifest fingerprint, indexes and bounds. A corrupt image is rejected before it can partially update the stored record.

Moving progress is a manual transfer. After import, the two browsers can change independently until someone exports and imports again. Both devices need to be available for that transfer. Automatic sync, shared workspaces and recovery after a wiped device would need a server, which I haven't built for this handbook.

The wire format and its tests live in the repo. Progress stays in the current browser, with QR export and import for moving it to another device.

```text
Question state: 00 not started · 01 in progress · 10 completed
150 questions × 2 bits = 300 bits = 38 bytes (rounded up)
```
