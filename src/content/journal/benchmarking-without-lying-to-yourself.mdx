A cache benchmark can flatter whatever policy you just wrote. I set up Cachewise's runs so both policies see the the same deterministic requests and logical capacity, with recency, recomputation cost and size pulling in different directions.

`computeCost` is a weight the caller supplies. The bench does not run the expensive work. That keeps the factory from dominating the timer while the cache policy is measured. A higher weighted hit ratio only translates into lower application latency when the real recomputation cost is measured too.

I kept the benchmark to three workloads:

- **Scan pollution.** A hot, expensive set sits near capacity while a large fraction of requests are cheap one-off keys. Does scan traffic kick out the entries you actually wanted to keep?
- **Skewed expensive reuse.** Access piles onto a small head of the key space, and that head is expensive. Sizes vary.
- **Byte pressure.** Small expensive entries fight large cheap ones for the same byte budget.

The clock is logical, so recency decay and sketch aging don't depend on the scheduler being in a good mood. Policy order alternates across trials so one policy doesn't always run warm. Warm-up runs are excluded from the measured samples. The report keeps the runtime, the machine, and every trial. JSON for the raw run, CSV if you want to argue with it in a notebook, Markdown for the short table.

The number I care about first is weighted hit ratio: cost-weight served by hits, over cost-weight requested. Raw hit ratio is context. A hit on an expensive key saves more work than a hit on a cheap one. Throughput and batch p50/p95 are there because the policy itself costs CPU. Those percentiles come from batch averages, so they describe batch timing rather than individual operations. Evictions and rejections show whether the cache made room or refused the insert.

One checked-in run, Node.js 26.13.0, Apple M4 Max, 100,000 ops, 256 KiB logical budget, seven measured trials, two warm-ups:

| Workload               |    LRU | Cost-aware |
| ---------------------- | -----: | ---------: |
| Scan pollution         | 63.84% |     99.02% |
| Skewed expensive reuse | 58.93% |     91.69% |
| Byte pressure          | 80.94% |     99.44% |

The cost-aware policy had a higher weighted hit ratio on all three workloads. Throughput was slower on the first two and faster on byte pressure.

`maxBytes` is the cache's accounting budget. Process RSS also includes runtime and object overhead. JIT, GC and machine load affect timings, so compare policies within the same run before comparing commits. GitHub-hosted runners are convenient, but noisy.

For an application decision, use a trace from that application and measure the factory itself, not just the cache bookkeeping.
