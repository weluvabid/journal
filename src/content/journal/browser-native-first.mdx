Installing a package is the fastest way to make a feature appear. It is often a bad way to own that feature. You inherit an API, transitive deps, upgrade churn, a licence, bundle bytes, and someone else's idea of the runtime. On the web, a lot of the toolbox is already in the browser. I want to know what that toolbox can't do before I wrap it.

Not an anti-library rant. A "name the missing capability" rant.

`URL` and `URLSearchParams` already parse query strings. The Clipboard API writes the clipboard, inside a secure context, with permission rules. File pickers and downloads exist. Workers exist when the main thread shouldn't do the work. `AbortController` is a cancellation signal you can thread through async calls. `structuredClone` covers a defined set of values; you don't need a homemade deep-copy until you step outside that set.

These APIs are not the same in a page, an extension, a service worker and a frame. Permissions differ. Lifecycles differ. Hiding that behind a dependency usually means the abstraction is lying about the environment.

Copy 2 Markdown is the concrete case. Tab access is `activeTab` after the user invokes the action. The clipboard write happens in an extension-owned offscreen document, not in the page. Extraction and Turndown don't need a server. Adding one would mean someone's copied page content leaves the browser, which is the opposite of the product.

A platform API tells you *how*. It does not decide *whether*. Clipboard writes still need a user gesture and a visible failure. A worker still needs a validated message and a rule for stale results. `localStorage` still needs a version, a quota failure path, and a defined response to garbage.

The wrapper I actually want is thin: normalize the error, narrow the interface, make the unsupported case explicit. A framework around `navigator.clipboard.writeText` is how small tools get fat.

I still pull in libraries when the problem is the library. Readability and Turndown stay in Copy 2 Markdown because article extraction and HTML-to-Markdown are full of edge cases I don't want to rediscover. "Fewer dependencies" is not a reason to fork that mess into our tree.

The bill is: bytes, maintenance, security, compatibility, licence, transitive surface, and what it costs to rip out later. A browser feature should not drag a server-only module into the client bundle because the import was convenient.

Before `pnpm add`, I write down the capability, the native API, the contexts where it fails, and the test that proves it. If that page is short, I use the platform. If it's a novel, I take the maintained library and put it behind a small boundary.
