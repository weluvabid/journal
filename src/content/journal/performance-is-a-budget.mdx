"It's slow" is a mood. A budget is a number: latency you're willing to spend, memory you're willing to keep, CPU, bytes on the wire. Until those exist, optimization is just fidgeting, and you'll "fix" the metric that's easiest to move.

Latency isn't throughput. You can do a lot of ops per second and still have a miserable p95. Payload size isn't heap size. Cachewise's `maxBytes` counts what the estimator says, not object headers and map overhead. Bundle size is transfer and parse. Main-thread CPU is what happens after the bundle is already there.

Say which number. Median is the typical call. p95 is the tail people actually feel. Peak memory catches the spike an average hides. A chart without the workload is decoration.

Cachewise is the example I keep coming back to because the budgets fight. A large expensive entry can evict several small ones. A policy can raise weighted hit ratio and lose throughput doing the bookkeeping. So the bench prints weighted hit ratio *and* throughput *and* batch latency. One blended "performance score" would let me hide the loss.

A hot loop isn't the bottleneck if you're waiting on the network. A smaller bundle doesn't help if a synchronous walk blocks the click. More concurrency helps until the next stage saturates, then it just grows the queue. Every change should name the resource it expects to save and the one it might spend.

Synthetic workloads are for isolating a question. They are not production. If the traffic shape changes, throw the conclusion out and measure again.

Sometimes the right result is doing nothing. Inside the budget, extra cleverness is complexity the user never sees. Move parsing to a worker, cap an input, bound history, shrink a payload — when a number says you should. Not because fast feels responsible.

*Example I'd add:* one Cachewise workload where weighted hit ratio goes up and ops/sec goes down, with both numbers in the same row.
