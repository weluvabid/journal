Once there are more pages than a sidebar can hold, search becomes part of how the site feels. A bad result list makes a useful library look like a junk drawer, so I build search alongside the content.

Frontend Atlas and this journal are mostly static. Search uses a JSON index with each entry's stable ID, title, summary, tags, search terms, normalized searchable text and route. The searchable text is generated from the article content, so the ranking code can work locally without fetching each article page.

Search terms give readers another way to find something when they use a different name from mine. Title and summary are what a person actually reads in the row. An exact title should beat an accidental mention. A tag hit can beat a common word buried in a long summary. Same query, same order, every visit. If the order wobbles I can't tell whether a tweak worked.

I keep the scorer small, with a few field weights. I try queries that should find a result and queries that should not; when a real mismatch shows up, I adjust the relevant weight. More constants won't make a better engine while the corpus fits in one JSON file.

Keyboard support is part of the search flow. Open it, type, move through results, activate one, close it. You can do the whole thing without a pointer, and focus stays put when the list changes. Empty query, no matches, and "index still loading" are three different states. A blank panel is me failing to say which one.

Reduced motion stays reduced. On a small screen the list scrolls inside the surface, and the surface has an exit. I keep the modal easy to dismiss; on a small screen, scrolling the index is often quicker.

What I'd actually measure: a handful of real queries, whether the top hit is the one I meant, whether keyboard alone finishes it, index bytes, time to first results. The current corpus fits the generated JSON index. If the payload grows, I'll measure it before adding a precomputed index or a server.

The ranking weights favour metadata over body mentions: exact title tokens score `32`, aliases `25`, tags `21`, summary `10`, and body mentions `2`. A full-title phrase match adds `55`, or `100` when the query exactly matches the title. That gives a named article a clear lead over an incidental mention in its body.
