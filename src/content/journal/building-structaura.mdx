A source hash changes because you fixed a comment or let the formatter breathe. Correct for bytes. Useless if the question is "did the syntax change?"

StructAura parses JavaScript or TypeScript with Tree-sitter, applies a small, versioned set of syntax-only normalizations, and hashes a canonical tree. Same Rust core on native and in the browser WASM build. I didn't want two fingerprint definitions that drift the moment the bindings do.

Matching fingerprints mean the canonical trees match for that language and normalization version. The fingerprint represents normalized syntax. It carries no type analysis, constant folding or proof that two functions behave the same.

Native Tree-sitter and `web-tree-sitter` use different runtimes, but both adapters emit the same flat preorder records: syntax kind, optional leaf text and the number of retained children. The Rust core rebuilds the tree and handles canonicalization, encoding and hashing for both paths.

```text
native parser   ┐
                ├─ records → Rust core → fingerprint
browser parser  ┘              (wasm-bindgen on the web)
```

The core rebuilds and walks the tree with an explicit vector in reverse preorder. That keeps deeply nested input out of the application call stack. Truncated records or leftover records return errors.

Version 1 drops comments and some anonymous punctuation, unwraps a single parenthesized expression, and strips string delimiters without decoding escapes. Child order stays. Escape spelling stays. Two strings with the same runtime meaning can still hash differently because their escape spelling is retained. Changing that rule requires a `normalizationVersion` bump so stored fingerprints keep their meaning.

The encoder uses domain tags, fixed-width big-endian integers, length-prefixed bytes and typed properties. Property keys are sorted; child hashes stay in source order. Hashing is iterative and Merkle-style, so a changed descendant changes the hashes up to the root. The root identity includes the format version, language and normalization version. `compareFingerprints` checks those fields before comparing digests. JavaScript and TypeScript fingerprints have different identities, even when their digest strings happen to match.

Recorded release-build numbers, 15 samples after warm-up: small inputs under about 116 µs median; ~64–70 KB inputs around 12–14 ms at p95. Stage timings for parse, canonicalization, encoding and Merkle hashing help locate work inside the pipeline. They are measured separately; instrumentation changes the run, so they cannot be added up to get the end-to-end time.

The browser package has an async `init()` because the WASM module and the grammars have to load. After that, fingerprinting is synchronous. Large files belong in a worker so parsing doesn't freeze the page.

Comments and selected punctuation are removed during normalization. Changes to the retained syntax change the digest. Semantic analysis belongs in a separate tool.

```js
// Same retained syntax; comments and layout differ.
const total = left + right;
```

```js
const total=left+right;
```

With the current JavaScript normalization version these formatting-only changes produce the same canonical fingerprint. Changing `right` to `tax` changes retained syntax and therefore the fingerprint. The fingerprints compare normalized structure; they do not tell you whether the programs behave the same.
