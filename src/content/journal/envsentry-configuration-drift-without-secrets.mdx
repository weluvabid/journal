A line diff shows that a config file changed. It misses a missing key, a duplicate assignment or a value with the wrong shape. EnvSentry compares dotenv, JSON and TOML after they're the same kind of document. The comparison code never learns which parser ran. The report never prints the values it compared.

Three crates, dependencies only downhill:

- `envsentry-core` — paths, values, documents, diagnostics, sensitivity. No files, no terminal.
- `envsentry-parsers` — dotenv, JSON, TOML into that model.
- `envsentry-cli` — args, read the files, pick a parser from the name, render, exit code.

CLI reads UTF-8, gets a `ConfigDocument`, asks core to compare, prints diagnostics. A new format shouldn't mean new branches inside the differ.

Entries stay in a `Vec` so duplicate keys remain visible to the differ. A map would erase that evidence before comparison. Containers get an entry at their own path *and* entries for children, so an empty object is still a structure, and an object isn't the same as a scalar sitting on that path. Array indexes are path segments.

Keys can contain dots, brackets, backslashes, control characters. Display escaping exists so the path you print isn't a second, ambiguous syntax. Control characters stay on one line. That's also so a path can't poke the terminal.

Dotenv parsing leaves the process environment untouched, and repeated assignments survive. JSON must be an object at the root, and repeated keys are kept, including nested ones. TOML duplicates die in the TOML parser. I don't reimplement that.

Core indexes paths with a `BTreeMap`. Missing, unexpected, repeated. If a path shows up once on each side, kinds are compared first, then the stored text. EnvSentry compares stored text exactly, so `01` and `1` produce a mismatch. Empty and whitespace-only values have their own check.

Diagnostics sort by path, code, severity, source, location. Same inputs, same bytes out. That's what makes a CI snapshot worth having.

Missing and duplicate keys are errors. Unexpected keys, empty values, value and type mismatches are warnings. `--strict` makes warnings fail the process and does not relabel them as errors. `check --schema` ignores value and type differences and still reports structure and empties.

| Finding | Default severity | `--strict` effect |
| --- | --- | --- |
| Missing key | Error | Still fails. |
| Duplicate key | Error | Still fails. |
| Unexpected key | Warning | Fails policy; remains a warning. |
| Empty value | Warning | Fails policy; remains a warning. |
| Value or type mismatch | Warning | Fails policy; remains a warning. |

Exit `0` means the policy passed. Exit `1` means findings failed it. Exit `2` means the tool itself failed because of bad arguments, an unsupported format, I/O, parsing or report writing.

EnvSentry reads the values into process memory so it can compare them. Text and JSON reports contain paths and diagnostics, never the old or new values. `ConfigValue` also redacts its raw field in `Debug` output, and parser errors don't echo input excerpts.

Core also exposes a `SensitivityPolicy` for names such as `PASSWORD`, `SECRET`, `TOKEN`, `API_KEY`, `DATABASE_URL` and `PRIVATE_KEY`, with case-insensitive matching and `*` patterns. Explicit entry classifications take precedence over path names, and array indexes are removed before classification. The built-in parsers mark entries `Unknown`, so the CLI does not use this policy yet. It omits compared values from every report.


The CLI reads each file in full before comparing it. I have parked line-and-column diagnostics and streaming input for a later pass.

```text
ERROR MISSING_KEY  DATABASE_URL  source=.env.example
ERROR DUPLICATE_KEY  API_TOKEN  source=.env
WARNING VALUE_MISMATCH  LOG_LEVEL
```
