An LSM usually gets sold as "buffer the writes, flush them sorted, merge later." TinyLSM is that sentence with the annoying parts still attached: tombstones, publish-before-clear, and recovery that will not treat a filename as a valid run.

Keys and values are opaque bytes. Empty keys and empty values are legal. A missing key is not an empty value, and a tombstone is not "this layer doesn't have the key."

The memtable is a `BTreeMap`. Writes land there. A read checks the memtable first, then walks immutable runs newest-first and stops at the newest record. If that record is a tombstone, the key is gone even when an older run still holds a value. Drop the tombstone too early and a deleted row comes back after flush.

Flush serializes an ordered snapshot into a new run and only then clears the memtable. If the write or the publish fails, the in-memory copy is still the only copy. Clearing first is how you lose data while believing you flushed.

`Engine::new()` is memory-only. `open(path)` is the disk engine. Flush and compact require the disk one. The public API takes `&mut self`. One writer, synchronous, no lock, no background thread. Two processes on the same directory are not a supported mode.

Runs stay immutable once published. On open, every discovered run is parsed before the engine is returned: bad headers, unknown tags, keys out of order, truncation, trailing bytes. Matching a filename is not enough.

A lookup may have to inspect several runs. There is no Bloom filter and no block index. That's a limitation I want visible. The project shows the shape of an LSM, not a production read path.

Compaction is a k-way merge of already-sorted inputs, so it doesn't dump records into a map and sort them again. Same key in multiple runs: the higher generation wins, tombstone included. TinyLSM keeps deletion semantics through compaction. It does not have snapshots or leveled compaction, so it also does not pretend it knows when a tombstone is safe to drop.

`Engine::inspect` exists so tests can see what was persisted instead of guessing from `get`. Failures are typed. Adversarial tests feed malformed files through recovery.

The bench reports median and p95 nanoseconds per item on selected workloads. `BENCH_ITEMS` and `BENCH_SAMPLES` change the size. It's a local baseline, not a cross-machine claim.

What I left out, on purpose: WAL, concurrent readers, background compaction, block cache, transactions, a network protocol. An educational engine that implies those guarantees is worse than a small one that doesn't.

```text
Flush publishes R2:  memtable [A, B] → empty; runs [R1] → [R2, R1]
Publish fails:       memtable [A, B] stays; runs remain [R1]
```

The memtable is cleared only after the new run is published. This describes the in-process failure path; it is not a claim of `fsync`-level crash durability.
