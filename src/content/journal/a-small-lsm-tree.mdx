There are three phases to the LSM: write to a buffer, flush to a sorted run, and merge. TinyLSM handles tombstone records, makes sure the run is published before the memtable is cleared, and checks that each run contains the expected data during recovery.

All keys and values are opaque byte slices. Keys and values can be empty. An empty value is not the same as a missing key. Tombstone records are used to show that a key has been deleted.

The memtable is a `BTreeMap`. When reading, the memtable will be checked first. Then the immutable runs will be scanned in order from newest to oldest. The newest entry will take priority. If the newest entry is a tombstone then the key will not exist. If a tombstone is removed too early during compaction then an older value can become visible again.

The flush function takes an ordered snapshot and serialises it to a new run. The memtable will not be cleared until after the run has been published. If there is an error while writing or publishing then the memtable will still be available. We don’t want to clear the memtable as we will lose our only live copy.

| Operation  | Data path                                                    | Failure or guarantee                                            |
| ---------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| Write      | Update the in-memory `BTreeMap` memtable.                    | No disk run is created until flush.                             |
| Read       | Check the memtable, then immutable runs newest-first.        | A newest tombstone hides older values.                          |
| Flush      | Serialize and publish a sorted run, then clear the memtable. | A failed write or publish leaves the memtable intact.           |
| Recovery   | Parse every discovered run before opening the engine.        | Malformed or truncated runs fail recovery.                      |
| Compaction | K-way merge sorted runs; the higher generation wins.         | Tombstones remain; there is no snapshot-aware safe-drop policy. |

`Engine::new()` creates an in-memory engine. To create a disk-backed engine we would call `open(path)`. We need the disk-backed engine to perform flushes and compaction. The public API takes `&mut self` so it is designed to be a single writer. There is no locking or background thread. Having two processes running against the same directory is not supported.

Runs are immutable once published. TinyLSM will parse all runs it finds when opening the engine. If there are any issues with the headers, unknown tags, unsorted keys, incomplete records or trailing bytes then recovery will fail.

When looking up a value it could scan through multiple runs. There is no Bloom filter or block index.

Compaction is a k-way merge of sorted runs. It will not load all the data into a map and sort it. If there are multiple runs with the same key then the record with the highest generation (including a tombstone) will be used. TinyLSM maintains deletion semantics as there are no snapshots or leveled compaction to determine if a tombstone can be safely removed.

`Engine::inspect` allows tests to see what has been persisted rather than guessing based on the return from `get`. Errors are typed. Adversarial tests will pass malformed files to recovery.

The benchmark shows the median and p95 of how many nanoseconds it took to process each item in the selected workloads. `BENCH_ITEMS` and `BENCH_SAMPLES` can be changed to alter the size of the workload and samples.

This version only handles the synchronous single-writer path. I have not included WAL, concurrent readers, background compaction, block caching, transactions or network protocol.

```text
Flush publishes R2:  memtable [A, B] → empty; runs [R1] → [R2, R1]
Publish fails:       memtable [A, B] stays; runs remain [R1]
```

The run file is synced before renaming. Syncing the parent directory is still on my durability TODO list.
