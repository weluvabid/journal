An LSM usually gets reduced to three steps: buffer writes, flush them in sorted order, merge later. TinyLSM also has to get the details right: tombstones, publishing a run before clearing the memtable, and checking each run's contents during recovery instead of trusting its filename.

Keys and values are opaque byte slices. Empty keys and empty values are both valid. A missing key is not the same thing as an empty value. A tombstone is a record too: it says the key was deleted, not that this layer has never seen it.

The memtable is a `BTreeMap`. Writes go there. Reads check it first, then walk immutable runs from newest to oldest. The newest record wins. If that record is a tombstone, the key is gone even if an older run still contains a value. Drop the tombstone too early and the deleted row comes back.

Flush serializes an ordered snapshot into a new run. The memtable is cleared only after that run has been published. If writing or publishing fails, the memtable remains available; clearing it first would throw away the only live copy before the replacement is ready.

| Operation  | Data path                                                    | Failure or guarantee                                            |
| ---------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| Write      | Update the in-memory `BTreeMap` memtable.                    | No disk run is created until flush.                             |
| Read       | Check the memtable, then immutable runs newest-first.        | A newest tombstone hides older values.                          |
| Flush      | Serialize and publish a sorted run, then clear the memtable. | A failed write or publish leaves the memtable intact.           |
| Recovery   | Parse every discovered run before opening the engine.        | Malformed or truncated runs fail recovery.                      |
| Compaction | K-way merge sorted runs; the higher generation wins.         | Tombstones remain; there is no snapshot-aware safe-drop policy. |

`Engine::new()` creates an in-memory engine. For a disk-backed engine, use `open(path)`. Flush and compaction require the disk-backed engine. The public API takes `&mut self`, so the model is single-writer and synchronous: no locking, no background thread. Running two processes against the same directory is not supported.

Once published, a run is immutable. When opening the engine, TinyLSM parses every discovered run before returning an engine. Bad headers, unknown tags, out-of-order keys, truncated records or trailing bytes make recovery fail.

A lookup may inspect several runs. There is no Bloom filter or block index, so reads can involve walking multiple runs.

Compaction is a k-way merge of already-sorted runs. It does not dump everything into a map and sort it again. If multiple runs contain the same key, the record from the highest generation wins, including a tombstone. TinyLSM preserves deletion semantics through compaction. There are no snapshots or leveled compaction, so it has no basis for deciding that a tombstone is safe to drop.

`Engine::inspect` lets tests examine what was persisted instead of inferring it from `get`. Errors are typed, and adversarial tests feed malformed files through recovery.

The benchmark reports median and p95 nanoseconds per item for selected workloads. `BENCH_ITEMS` and `BENCH_SAMPLES` control the workload size and sample count.

This version covers the synchronous single-writer path. I have left the WAL, concurrent readers, background compaction, block cache, transactions and network protocol out of it.

```text
Flush publishes R2:  memtable [A, B] → empty; runs [R1] → [R2, R1]
Publish fails:       memtable [A, B] stays; runs remain [R1]
```

The run file is synced before rename. Parent-directory sync is still on the durability backlog.
