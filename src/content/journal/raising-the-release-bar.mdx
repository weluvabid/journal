A happy path is how you demo. It is not how you ship. If the only proof is "I clicked it once and it worked," the release bar is the user's patience.

Unsupported states should fail in the open. Wrong version, unknown enum, malformed file, duplicate id: error, not a guess that happens to look like success. Silent continuation is how you corrupt state and then blame the next request.

The interesting tests are the ugly ones. Empty input. Duplicates. Maximum sizes. Cancel. A factory that returns after `delete`. Partial failure. A flush that dies on the way to disk. An import that must not mutate progress if the QR is junk. For the combinatorial stuff I use generated cases, but the count is not the evidence. The invariant and an independent expected result are.

Errors need to say which operation failed without pasting secrets into the log. EnvSentry's reports don't include config values for that reason. A retryable miss is not a validation error. Don't collapse both into HTTP 200 with a sad string.

Lint, types, tests, format, audit, the production build: different nets. Passing one doesn't pass the others. If a check didn't run, say so. A green suite on the wrong Node version is a note, not a release.

Ops counts too. Rollback, config, what it costs to stay warm, what happens when the worker is faster than the thing it writes to. FulfillmentGuard is where that stops being abstract: a message can fail three hops away from the click, and "we'll just retry" without idempotency double-applies the work.

I can't promise software won't fail. I can refuse to ship a boundary I haven't looked at, and I can refuse a failure mode that pretends it succeeded.
