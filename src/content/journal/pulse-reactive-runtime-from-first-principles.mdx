Frameworks make reactivity look like an API. Under it: a value changes, derived values go stale, effects run. Pulse keeps the API to four functions and leaves component composition to the application.

`signal` is mutable state. Read it inside a computation and you subscribe. Write it and dependents are stale. `computed` is lazy. Invalidation walks the graph; the function runs when someone reads. `effect` runs immediately, tracks what it read, reruns synchronously when those deps change, and the disposer plus `onCleanup` is how you don't leak the previous run. `batch` holds the flush until the outermost batch ends, so two writes don't publish an intermediate state.

```ts
import { batch, computed, effect, signal } from '@weluvabid/pulse';

const count = signal(0);
const doubled = computed(() => count() * 2);
const dispose = effect(() => console.log(doubled()));

batch(() => {
  count.set(1);
  count.set(2);
});

dispose();
```

A push-only system can recompute values nobody reads. A pull-only system has to check freshness on every access. Pulse splits the work: writes mark dependents stale, and reads refresh computed values when needed. Effects run synchronously through the scheduler after the update boundary. Nested `batch` calls wait; the outermost one flushes.

Each effect run collects the dependencies it actually read and replaces its previous set. When a conditional branch changes, subscriptions from the old branch are removed, so writes to those signals stop scheduling the effect.

Before a rerun, child effects are disposed and cleanups run in reverse registration order. The disposer is idempotent and pulls the effect off its dependencies. The scheduler dedupes queued effects with a `Set`. There's a bound on synchronous re-entry so a cycle doesn't pin the thread; failures get collected and the rest of the queue still gets a turn.

`onReactiveEvent` exposes event types and runtime IDs, never application values. Listener errors are caught so instrumentation cannot interrupt the scheduler.

Pulse handles reactive state and effect scheduling. Rendering and component lifecycles stay with the application. Effects run synchronously, so a slow effect still blocks the JavaScript agent; batching only controls when queued effects flush.

The tests I care about are the annoying graphs. Conditional deps, nested batches, cleanup order, dispose during an update, a listener that throws. Benchmarks should split runtime bookkeeping from whatever the effect did, or the numbers are just "your console.log is slow."

```ts
const usePrimary = signal(true);
const primary = signal('A');
const secondary = signal('B');

const dispose = effect(() => {
  console.log(usePrimary() ? primary() : secondary());
});

usePrimary.set(false); // next run drops primary and tracks secondary
dispose();
```

The dependency set is rebuilt on each run. Once the flag flips, later writes to `primary` should no longer schedule this effect.
