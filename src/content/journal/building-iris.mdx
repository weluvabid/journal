I was getting tired of rebuilding the same buttons, dialogues and form spacing every time I needed a UI. Iris is a boring package I pulled out to allow Pulse, Frontend Atlas and the journal to use the same primitives, without sharing a brand.

Iris allows me to have a shared set of components across my Svelte projects. The application will have ownership over the routing, composition and state. If Iris takes ownership of the navigation then I have done it wrong.

I’m using `shadcn-svelte` primitives to create dialogues with focus trapping, positioning for popovers and keyboard functionality for menus. There are many edge cases to consider in interactions like this, so it’s good that the primitives already have this built in. I’m using Iris to compose, add tokens and share the parts that should look similar between projects.

I’m still required to understand what the primitive is doing. Dialogues aren’t just a box with an X and comboboxes aren’t just an input and list. The primitive takes care of focus trapping, closing, keyboard functionality and accessibility roles. The title, items and meaning of the items come from the application. The styling can change but the focus ring and accessible name must remain.

If I’m unsure about what the component is doing I’ll build it out on its own. I’ll use `Tab` and `Escape`, look at the DOM and make sure that the accessible name remains. By rewriting all the primitives I’d be taking on years of edge cases. So I’ll keep the interactions within the primitive and compose and style for the product using Iris.

I’ve kept the visual design simple with light and dark themes using the same tokens. The labels remain readable, errors visible and spacing consistent. Using Tailwind means all the styles are part of one system. Consumers won’t have to pass lots of props to recreate the button.

The demo shows how the package can be installed, composed and themed. If the demo becomes more interesting than the library I’ve accidentally created a second product.

The package boundary is the product. It has clear exports, peer dependencies and no styles that dig into unknown parts of the repo. It can be installed as a tarball into an empty project. Version `0.4.1` on npm was the first useful checkpoint. The component set can be expanded without affecting the package boundary.

A component is reusable if it has clear responsibilities in its API, you know how it will behave with accessibility, it has clear dependencies and can be tested for failure. I’ll test the package by installing the tarball.

I want to keep Iris small and composable. The primitives should be clear and the next application should have its own identity. Success is having another repo that can take the dialog and understand what it is doing.
