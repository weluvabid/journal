I got tired of rebuilding the same buttons, dialogs and form spacing every time a project needed a UI. Iris is the boring package I extracted so Pulse, Frontend Atlas and the journal could share primitives without sharing a brand.

Iris gives my Svelte projects a shared set of components and a consistent base. The app still owns its routes, page composition and state. If Iris starts owning navigation, I've built the wrong thing.

I use shadcn-svelte primitives for dialog focus traps, popover positioning and menu keyboard behaviour. Those interactions have plenty of edge cases, and the primitives already handle them. Iris sits on top: composition, tokens, the bits that should look related across my projects.

I still need to understand the primitive I'm composing. A dialog is more than a box with an X, and a combobox needs more than an input beside a list. The primitive handles focus trapping, dismissal, keyboard behaviour and accessibility roles. The app supplies the title, items and their meaning. Styling can change, but the focus ring and accessible name have to survive.

When a component's contract is unclear, I test it on its own before using it in a page. I try Tab and Escape, inspect the DOM, check where focus goes, and make sure the accessible name survives composition and theming. Rewriting every primitive would mean taking on years of edge cases. I keep those interactions in the primitive and let Iris handle composition and product styling.

I kept the visual system monochrome, with light and dark themes built from shared tokens. Labels stay readable, errors stay visible, and spacing follows the same rules across components. Tailwind keeps the styles in one system without giving every consumer a pile of props to reinvent the button.

The demo shows the package being installed, composed and themed. If the demo gets more interesting than the library, I've started a second product by accident.

The package boundary is the product: stable exports, explicit peer dependencies, styles that don't reach into undocumented repo paths, and a tarball that installs in an empty project. Version 0.4.1 on npm was the first useful checkpoint; the component set can keep growing without changing that boundary.

A component is reusable when its API makes the responsibilities clear, its accessibility behaviour is understood, its dependencies are easy to follow, and its failure modes can be tested. I test the package itself by installing its tarball into an empty project.

I want Iris to stay small and composable. The primitives should stay visible, and the next app should keep its own identity. Success is another repo being able to take a dialog, understand its contract and move on.
